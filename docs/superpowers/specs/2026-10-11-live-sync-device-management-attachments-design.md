# Harmony Work 双端实时协作、设备管理与附件设计

日期：2026-10-11
状态：待书面审阅

## 目标与边界

本规格延续 2026-10-09 的统一会话设计。手机仍负责判断何时调用电脑，并在电脑完成后生成该轮最终助手答复；Windows 与手机可在同一共享会话继续对话。电脑执行期间，双方要立即看到可信的进度，电脑完成时双方先看到电脑成果卡。手机不在前台不妨碍电脑显示成果；手机恢复后再调用手机模型完成总结。

工作分为三个可独立验收的阶段：A. 实时任务状态与消息同步；B. 双向设备管理；C. 电脑文件附件。按 A、B、C 顺序交付。现有 11.29 服务只保存会话、任务、事件和附件元数据，不保存文件字节。附件只在电脑在线且手机与电脑建立直连时可预览或下载；无服务器文件中转或 TURN 文件中转。

## 当前断点

Windows 领取手机任务后使用隐藏的 mobile_executor 会话运行 Codex。Codex JSONL 事件直到执行完成才在后台运行器中汇总，进度不会进入共享会话。任务完成只写任务接口，且 worker 只在领取、导入或上传消息时通知桌面 UI。手机每约十秒轮询任务和会话；Android WebView 退到后台后不能保证继续运行。因此文件可已生成，但桌面会话无执行过程、无成果卡，最终答复要等手机重新活跃才出现。桌面聊天页只在切换会话或收到粗粒度 mobile_bridge_updated 事件时加载消息；服务端新消息与活跃任务状态并未稳定驱动当前会话和会话列表。已有 WebRTC DataChannel 仅传刷新提示，不能作为可靠状态源。

## 方案选择

方案 A：将现有轮询缩到一至两秒，并在完成时主动刷新。改动较少，但手机后台、Windows 重启和网络抖动仍会产生状态空白；全量拉取会话页也增加服务压力。

方案 B（采用）：11.29 持久化会话内的任务事件，以服务端序号作为顺序和恢复游标。两端使用带设备认证的 SSE 获取变更提示，断线后按游标补拉；前台短轮询和 P2P 提示作加速/兜底。电脑实时上传经过筛选的执行事件，完成时原子写入任务结果与成果事件。消息仍沿用原有逐条消息表与 seq，任务事件不伪装为助手消息。

方案 C：完全通过 P2P 传进度与文件。延迟低，但 NAT 穿透、后台挂起和重连后的历史补齐无法保证，不适合作为任务真相源。

## 阶段 A：任务事件与即时同步

服务端新增按账户、会话、任务关联的事件表。每条事件由服务端分配递增序号和时间，包含稳定事件 ID、类型、简短公开摘要及必要的结构化字段。允许的状态为 queued、claimed、planning、tool_started、tool_finished、artifact_ready、succeeded、failed、cancelled。工具事件只保留用户可看的名称、阶段、简短结果和成果文件名；不传模型内部推理、原始命令输出、凭据、完整本地路径或大量日志。每条摘要最多 512 字符、结构化载荷最多 2 KiB、每任务最多 500 条事件；高频输出在电脑端按 500 毫秒合并，终态与成果事件不得丢弃。过程事件保留 90 天，终态和成果卡随任务保留。事件写入使用任务租约和幂等事件 ID；租约失效后旧 worker 不得继续发布事件或覆盖新结果。

Windows 的 Codex exec 读取 JSONL 时即映射公开事件，写入本机当前共享会话的任务投影，并异步上报服务端。上报失败进入有界本地待发送队列，重连后按 ID 重试。执行进度与手机任务绑定，不在普通会话里建立可见的第二套对话。原始执行上下文仍留在隔离的内部 Codex 线程。任务完成时服务端在同一事务更新任务状态并写入最终成果事件，避免完成状态与成果卡不一致。结果正文保持原有任务接口；成果卡包含任务摘要、完成/失败时间、可公开结果摘要和已登记附件。手机模型最终答复作为独立助手消息写入原共享会话；若手机离线，成果卡持续可见，状态写为“电脑已完成，等待手机整理”。

两端用带 Cookie 与设备令牌的 SSE 接收会话消息、任务事件、设备变更的轻量提示。SSE 不承载全部正文，只携带最新序号；客户端调用增量接口补齐，重放按消息 ID 或事件 ID 幂等合并。连接断开或应用恢复前台时从持久游标补拉；SSE 不可用时前台每三秒轮询，后台不依赖 WebView 定时器。WebRTC 提示保留为低延迟加速器，不作为唯一交付路径。服务器需要禁用该 SSE 路径的 Nginx 代理缓冲并发送心跳，部署后分别验证服务直连与公网入口。

Windows 活跃共享会话显示任务流程卡：等待电脑、准备/规划、正在使用工具、已生成成果、等待手机总结、完成或失败。卡片以发起消息 ID 和轮次 ID 锚定在对应用户消息之后，手机最终助手答复仍在卡片之后；消息 seq 与事件 seq 分别排序，不把两种序号直接比较。会话列表在任务未结束时显示运行标记，异常和离线状态用文字说明；即使当前选中会话不切换也实时刷新消息和卡片。手机同一会话显示相同阶段与成果卡，任务页只保留索引入口。重复消息按 ID 去重，按服务端 seq 排序；失败的 SSE/轮询不能让旧响应覆盖较新界面状态。电脑自身在共享会话发言继续沿用单轮租约，不因进度事件产生第二个助手答复。

验收：手机下发文件任务后，电脑会话与列表在领取后及时显示运行状态和至少一个安全执行步骤；手机退后台时电脑仍立即显示电脑成果卡；手机恢复后只生成一次最终总结。两端不切换会话即可看到对方新消息；断网重连、进程重启与重复事件均不丢失、不重复。错误和审批拒绝显示失败，不伪称完成。

## 阶段 B：双向设备管理与命名

现有 GET /devices 已返回绑定关系。新增按 desktopDeviceId 与 mobileDeviceId 删除绑定关系的接口，要求登录账户、发起设备有效令牌及其参与该绑定；操作幂等。解绑时停止该关系的同步、取消其排队任务并使正在执行任务的后续结果/附件授权失效；其他手机与同一电脑的绑定不受影响。服务端保留会话历史，不因解绑删除消息。客户端及时清除失效的默认设备选择、直连通道与本地任务入口，显示“已解除绑定”；手机本地会话缓存仍留给用户。

新配对在电脑已持有有效设备身份时复用同一个 desktopDeviceId，而不是每扫一台手机就创建一个新的电脑设备并覆盖本地 ID。无有效设备身份时才创建。桌面“连接手机”面板列出该电脑绑定的手机名称、绑定状态和解绑动作；手机“我的设备”列出电脑名称、默认执行电脑与解绑动作。解绑前显示目标设备名和后果，再执行服务端删除；两个客户端通过设备变更提示刷新。对历史版本产生的多个电脑设备 ID，不在后台推测或自动合并；用户可重新配对到当前设备身份。执行中的任务在解绑后进入 cancelled；电脑 worker 在续租收到撤销结果时终止 Codex 子进程，不再尝试上传成果。

桌面名称取 Windows 实际设备名，最长 80 字符并做显示转义；获取失败才用 Harmony Work Windows。桌面启动时可更新自己的服务端名称，旧的通用名称在下一次启动后刷新。手机名称可先沿用当前 Android 名称。设备列表禁止展示令牌和配对密钥。

验收：同一电脑依次绑定两台手机，桌面列表显示两台，手机各显示 Windows 设备名；任一端解绑其中一条关系后两端列表同步，其余绑定仍正常；失效设备无法继续读写会话、领取任务或下载附件。

## 阶段 C：电脑文件附件

Windows Agent 找到目标文件后，调用新增的 WorkBuddy MCP 分享文件工具登记附件。模型只传文件路径和展示名；当前任务及会话身份由桌面运行时提供的受信上下文绑定，不能由模型自行指定。该能力检查文件存在、大小、类型和路径权限，只接受当前任务允许访问的工作区文件或已由现有桌面授权机制明确允许的其他文件；不根据聊天正文猜测路径并直接开放任意本地文件。登记后的本机私有映射保存附件 ID、规范化真实路径、文件大小和校验摘要。11.29 只保存账户、会话、任务、来源电脑、附件 ID、展示文件名、MIME、大小、摘要、创建时间与撤销状态，绝不保存本机绝对路径或文件字节。卡片在两端同一任务成果下呈现；普通桌面会话的现有成果文件行为不被改变。

手机点预览/下载时，先向 11.29 申请短时单次传输票据。服务端检查当前账户、手机令牌、有效绑定、会话和附件归属。手机经现有 WebRTC 协商建立独立文件 DataChannel，向指定电脑发送附件 ID、票据和传输偏移；电脑再向服务端核验票据及绑定，确认本地文件仍与登记时的大小/摘要一致后分块传送。票据只授权该文件给该手机，过期、解绑和任务撤销后不可用。分块传输使用背压、限速、取消和断点续传；完成后手机核对长度与摘要。文件仍保留在电脑，手机缓存供本次预览，用户选择下载时保存到 Android 可访问位置。

首版附件上限为 200 MiB；图片、PDF 和文本可在手机缓存后预览，其他类型提供下载与系统打开。超限、文件移动/修改、权限变化或电脑离线时卡片显示明确原因。若 P2P 直连失败，附件保持不可下载状态并提供重试；不偷偷改走 11.29、腾讯云或 TURN 传文件。文件名和预览文本按不可信内容处理，拒绝路径穿越与危险 MIME 伪装；下载不自动执行文件。

验收：用户在手机同一会话要求找到电脑上的指定文件，Windows Agent 登记并在任务成果中返回附件卡，两端均可见；手机通过直连预览或下载并校验内容。另一账户、已解绑手机、伪造票据和被替换的本地文件均不能取到字节；电脑离线/P2P 失败时不出现假下载成功。

## 测试、发布与风险

服务端覆盖授权、解绑、事件幂等/重放、租约失效、附件票据和状态事务测试。Windows 覆盖 JSONL 公开事件映射、任务投影、设备复用、文件路径约束和附件直传；Android 覆盖消息/事件合并、前后台恢复、默认设备回退、卡片状态、下载校验。三端各自构建并在 MuMu 与实际小米设备上走一条“手机发起、桌面执行、电脑成果先显示、手机最终总结”的完整链路，再走文件预览/下载与双向解绑。测试安装包单独标识，不覆盖现有 1.0.9 验收包；正式全量包在跨端验收后生成。

最大风险是某些公网 NAT 环境无法建立直连。按用户选择，附件在这种情况下不可用；任务事件和文本消息仍经 11.29 可靠同步。Android 后台恢复时最终总结可能延后，但电脑成果卡立即可见。上传的公开事件必须经过白名单与长度过滤，避免泄露内部推理和本地敏感数据。
