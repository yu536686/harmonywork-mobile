# Harmony Work 手机与 Windows 统一会话设计

日期：2026-10-09

## 目标与范围

手机只有一个对话输入入口。手机端小亨使用个人账户的 Harmony Responses 配置独立处理轻量问题；需要电脑文件、应用或本地工作环境时，由模型调用已绑定 Windows 设备执行，取得结果后仍由手机端小亨完成该轮答复。用户不必把草稿转到“交给电脑执行”表单。

手机发起的会话是两端可继续的共享会话。手机发送的用户消息、手机独立生成的答复、电脑端用户主动发送的消息及其答复，都出现在同一会话中，保留相同会话 ID 和服务端顺序。Windows 会话列表继续标注“手机端”。本设计只同步手机发起的共享会话；桌面端原有的其他本地会话不自动上传到手机。

任务页只提供跨会话的任务进度、失败原因与成果索引，点击任务返回原会话。Harvis 生图、技能管理和记忆的实际能力不在本次实现范围；现有入口保持原状。

## 交互流程

1. 用户在手机会话输入内容，消息立即保存在本机并进入待同步队列。在线时写入 11.29 服务端消息流；状态区区分“发送中”“已同步”“等待网络”。
2. 手机调用 Harmony Responses。模型可直接返回文字，或调用唯一的 `execute_on_desktop` 工具，参数是明确、有限的执行目标及所需上下文。客户端校验工具名、参数长度和设备绑定状态，只向当前选中的已授权 Windows 设备创建任务；模型不能下发任意设备 ID 或绕过桌面现有权限策略。
3. 远端任务在当前会话内显示状态卡片：等待电脑、执行中、等待手机整理、已完成或失败。状态卡片不作为普通用户/助手消息存储。“任务”页展示同一任务的摘要。
4. Windows 领取任务，在与共享会话分离的内部执行上下文中运行现有 Agent，并按现有本地确认策略处理文件和命令操作。原始执行结果与错误返回任务接口，不直接写成共享会话的助手答复。
5. 手机收到结果后，把工具调用和结果按 Responses 协议交回模型，由手机端生成最终答复并逐条同步。失败结果同样作为工具结果交回模型，使小亨能说明哪些工作未完成，不伪称成功。
6. 用户在 Windows 打开该共享会话时可正常继续输入。桌面端本地模型完成该轮答复，新增的用户/助手消息同步到服务器，再回到手机。两端在同一会话内按服务端顺序展示。服务端为共享会话提供带租约的轮次占用：两端开始模型处理前先领取轮次；已有运行中轮次时，两端显示占用状态并阻止新一轮发送，直至该轮完成、明确失败或租约恢复。

手机未绑定电脑时仍能独立对话。遇到必须访问电脑的需求，模型说明需要先绑定设备，并保留原用户消息供绑定后重试；不会伪造已执行结果。已绑定但 Windows 离线时，任务持久排队，手机显示等待状态，电脑重新在线后领取。已绑定的共享会话在协调服务暂不可用时，本机保存输入并标记“等待同步”，恢复连接并领取轮次后才调用模型，避免两端离线时同时生成互不知情的答复；未绑定的本地会话仍可直接调用手机模型。

## 服务端会话协议

11.29 的 `remote.harmonywatch.cn/api/mobile` 继续提供账户 Cookie、设备令牌和已绑定关系校验。`workbuddy_mobile_sessions` 保存共享会话元数据和归属手机设备；新增逐条消息表，以 `(user_id, session_id, message_id)` 唯一约束实现幂等写入。服务端为每条消息分配单调递增的 `seq`，并记录角色、内容、来源设备、创建时间及可选的轮次 ID。仅允许 `user`、`assistant` 两种可见角色；内部工具调用、推理和桌面执行日志不写入可见消息表。

新增 `POST /sessions/:id/messages` 逐条追加、`GET /sessions/:id/messages?afterSeq=` 增量读取及 `GET /sessions` 会话列表；列表返回最新 `seq` 和更新时间。新增按会话领取、续租和完成轮次的接口，使用稳定的轮次 ID、发起消息 ID 与有效期，服务端原子保证一个会话只有一个活动轮次。任何写入和读取都同时校验账户、设备令牌及其绑定关系。相同消息 ID 重试返回既有记录；相同 ID 但内容不同返回冲突。服务端顺序是两端显示顺序，客户端时间只用于本地待同步提示。会话标题由首条用户消息生成，后续可通过单独的标题更新接口修改，不通过整段快照覆盖。

现有 `PUT /sessions/:id` 快照接口在过渡期保留：收到旧客户端快照时逐条将其消息幂等导入新消息表，绝不删除或覆盖已有桌面消息。现有 JSONB 历史消息一次性按原数组顺序迁入；重复迁移不产生重复消息。新客户端只使用增量协议。确认旧版客户端淘汰后再删除快照读写路径。

远端任务保留现有租约、心跳和幂等机制，并增加轮次 ID、工具调用 ID、结果归属信息。服务端持久保存任务状态和结果；手机重启后可以按会话恢复待处理轮次。结果只返回已绑定的发起手机，不因桌面多次上报而产生多条最终答复。服务端只保存轮次与任务的关联，不保存 API Key、登录密码或模型响应项。

## 两端状态与同步

手机本地会话缓存增加服务端 `seq` 游标、待发送消息队列和待完成轮次。每次登录、设备配对、应用恢复前台及定时轮询时，先补发本地待写入消息，再拉取服务端新消息；按消息 ID 合并，按 `seq` 排序。服务端已确认的消息在本地缓存中保留；切换账户时依账户 ID 隔离。手机仅对自己发起的轮次运行手机模型，桌面主动回复不触发手机再生成一条答复。

Windows 同步器把服务端消息按原消息 ID 和 `seq` 导入本地 `source=mobile` 会话；本地用户主动发送及桌面 Agent 完成的可见消息反向上传。导入记录标记为远端来源，避免回传循环。仅比较消息内容来去重会误删合法的重复答复，改为严格按消息 ID 去重。桌面内置 Agent 的历史和内部执行上下文分别管理；代执行任务不复用共享会话的 Agent 线程，也不在共享会话中追加内部提示或原始结果。

已有 WebRTC DataChannel 只用于提示另一端立即刷新。11.29 服务端持久消息流和任务队列是可靠路径；P2P 失败、应用后台或 Windows 重启不改变消息及任务语义。

## 模型调用与恢复

手机 Rust 端扩展现有 `mobile_chat` 为可返回“文本答复”或“电脑工具调用”的结构化结果。工具声明采用 Harmony 网关支持的 OpenAI Responses function calling 格式。调用结果需要保留 `call_id`，在任务完成后使用 `function_call_output` 继续该轮响应；当请求使用 `store: false` 时，客户端重放必要的输入、工具调用输出及模型要求保留的响应项。首轮工具调用及继续调用都设置有界超时、上下文条数和输出长度，并只显示最终助手文本，不显示 reasoning 或工具内部数据。

每轮使用稳定的轮次 ID 和任务幂等键。手机在任务提交前于本机持久化 `call_id` 和继续请求所需的最小响应项，收到任务确认后记录任务 ID；进程重启后结合本机状态与服务端任务状态恢复。若本机模型响应项丢失，任务成果仍可查看，但不会自动重放可能产生新工具调用的首轮请求。电脑任务完成而手机暂时离线时，最终答复在手机恢复网络及模型服务后生成。模型继续调用失败时任务成果仍可从状态卡片查看并重试“整理结果”，不会重新执行电脑任务。首版每个手机轮次最多调用电脑一次；继续请求禁用电脑工具，避免循环执行。

部署前以测试账户验证当前 Harmony 网关的 function calling 与 `function_call_output` 兼容性；若网关不支持，明确报错并暂停远端自动执行，不悄悄切换为关键词路由。

## 安全与数据边界

手机解密的个人 API Key 只在 Rust 内存中使用，不经过 11.29 协调服务，也不包含在任务、二维码或同步消息中。服务器仅接受当前账户下有效配对设备的读写。桌面执行沿用现有本地授权设置；来自手机模型的任务目标被视为不可信输入，桌面 Agent 对文件和命令仍执行权限检查。对消息、任务目标、结果和分页均设置大小上限。设备解绑或账户退出后停止同步，清除进程内凭证及未授权的待执行状态。

## 验收标准

1. 手机发送“帮我解释这段文字”时，不调用电脑，手机答复同步出现在 Windows 对应的“手机端”会话；Windows 再发送一条消息及收到答复后，手机能看到这两条消息，顺序一致。
2. 手机发送“读取电脑上的指定项目并总结”时，模型发出工具调用；Windows 领取并执行；手机显示排队、执行和整理状态，最终只出现手机模型整合后的一个助手答复。任务页可回到原会话。
3. Windows 离线、手机进后台或应用重启期间，已提交任务不丢失；恢复后不会重复创建任务、重复执行或重复生成答复。网关继续调用失败可重试整理，而不会重新执行电脑任务。
4. 两端断网后重连，消息按 ID 去重并按服务端 `seq` 收敛；相同内容的两条合法消息均保留。旧版手机快照迁移后不会覆盖桌面续聊内容。
5. 用未绑定设备、其他账户和伪造设备令牌请求消息或任务接口均被拒绝。手机 API Key 不出现在服务端记录或同步载荷。
6. 服务器协议测试、手机前端及 Rust 测试、Windows 相关测试和构建通过；Android Debug APK 与 Windows 安装包在可用环境打包，并对实际绑定设备完成端到端验证。若某一设备暂不可操作，单独记录该验收项的实测限制。

## 实施顺序

先迁移 11.29 服务端消息协议并验证旧版兼容；再实现手机的增量同步、工具调用与恢复；随后实现 Windows 的反向同步和隔离执行；最后移除两个“交给电脑”输入入口，打包并进行两端真实会话验收。服务器接口先兼容旧客户端，待新 Android 与 Windows 版本均可用后再切换正式流量。
